# Admin color system (ODD feature)

Objective: make the admin web interface readable and brand-coherent under the Astryx design system (already installed and wired), starting from the reported defect of white text on white backgrounds, and decide the color direction with the gentle-design / gentle-ui-design skills before applying it to the app.

## Specs

- S1: "tenemos que trabajar en los colores ya que hay cierto texto en blanco con fondo blanco" — no text may render white or near-white on a white or near-white surface in the admin app, in any color mode.
- S2: "podemos usar gentle design y gentle ui design" — the color direction is produced with the gentle-design and gentle-ui-design skills: artboards under `design/<slug>/`, tokens taken from the project design system, UX self-check applied.
- S3: The admin app already runs Astryx `@astryxdesign/core` + `@astryxdesign/theme-neutral` ("neutral"), wired in `apps/admin/src/main.tsx` with cascade layers in `apps/admin/src/layers.css`; the color system must live inside that design system, not beside it.
- S4: Astryx agent docs (`apps/admin/AGENTS.md`) govern how new UI is built: start from a template, no raw `<div>` for layout, component props before utilities, tokens before raw values.
- S5: Existing admin screens (13 routes) and the API contract stay intact; the color work changes presentation only.

## Log

- L1: "Excelente ahora se ve mejor pero tenemos que trabajar en los colores ya que hay cierto texto en blanco con fondo blanco, podemos usar gentle desing y gentle ui desing"
- L2 (evidence): The Astryx `Theme` wrapper sets `color: var(--color-text-primary)` on a `display: contents` element (`node_modules/@astryxdesign/core/src/theme/Theme.tsx`). The neutral theme defines that token as `light-dark(#000000, #ffffff)`, and `Theme` syncs `data-theme` on `<html>` from `mode` (default `system`). With the OS in dark mode the inherited text color becomes white, while every app surface stays hardcoded light (`bg-white`, `bg-slate-50`) → white text on white cards. The app never sets a color of its own on those cards, so the bug is inherited, not a `text-white` class.
- L3 (decision): C.T1 mitigates with the design system's own mechanism (explicit light mode) plus an explicit app text color; the durable fix belongs to the direction chosen in C.T3/C.T4.
- L4 (evidence): The installed `neutral` theme is a grayscale system (`--color-accent: light-dark(#1b1b1b, #f1f1f1)`, no brand hue), which conflicts with the project's existing "Mercado fresco" palette (emerald `brand`, carrot `accent`, corn `highlight`). C.T3 must make that trade-off explicit.
- L5 (C.T1 done): Fixed with the design system's own mechanism — `<Theme mode="light">` so `data-theme="light"` keeps `light-dark()` on its light half — plus explicit text color on the app shell (`text-slate-900` on the Layout root and the login root) so no surface depends on an inherited color.
- L6 (C.T2 done): `design/system.md` re-synced; sources are now the Astryx `neutral` theme, the `Theme` component contract, the Tailwind config and the admin global stylesheet. `design/system.html` renders both halves of the color tokens plus type, spacing, radius, elevation and core components.
- L7 (C.T3 done): Design `design/admin-colors/` with three directions — `01-astryx-neutral.html` (adopt the system as it is), `02-mercado-fresco.html` (keep the brand palette), `03-verdu-sobre-astryx.html` (own theme extending `neutral`, one token family for both modes). The human picks one before C.T4.
- L8 (handoff, human's choice): "Implement the design artboard design/admin-colors/02-mercado-fresco.html" — direction 2, "Mercado fresco": color as identity, gradient band, tinted table headers, status chips, visible elevation. Handoff target `admin-colors/02-mercado-fresco.html`, reported through the `gentle_design` tool (`in_progress` at the start, `implemented` at the end). The handoff commits nothing.
- L9 (C.T4 mapping): Artboard parts mapped to the project stack, not copied: sidebar → `Layout.tsx` (brand-900 background, `h-1` gradient strip `brand-500 → accent-600 → highlight-500`, inactive nav `text-brand-100`, active `bg-white/10` + `border-brand-500`, footer `bg-white/10`); gradient band → new full-bleed band in `Layout.tsx` that carries the crumb, the route title and today's date, so every page stops rendering its own `h1` (11 page files updated); KPI cards / tables / badges / alerts → `DashboardPage.tsx` with `rounded-xl`, `shadow-sm`, `bg-brand-50` table headers and `border-l-4 border-l-red-600` alerts. Neutral surfaces come from a `slate` remap in `apps/admin/tailwind.config.js` (`50 #f4f7f4`, `100 #eef1ec`, `200 #e6ebe5`, `300 #e2e8f0`), so the other eleven screens follow the new surfaces without touching their markup.
- L10 (deviations from the artboard, deliberate): the artboard's "Exportar" button was not implemented — the admin API exposes no export action and inventing one was out of scope; the artboard's info-toned alert (carrot border) was not applied because the `Alert` type carries no severity field, so every alert keeps the error tone; the primary action uses `brand-700` (#047857, 4.77:1) instead of the artboard's `brand-600` (#059669, 3.13:1), because 12px button labels need AA; the artboard's "LV" square was mapped to the project's existing `TomatoMark` SVG; the band crumb reads "Todas las sucursales" because the shell has no branch context, and the artboard's per-branch counts stay in the dashboard body.
- L11 (palette consistency applied to the remaining screens): every primary button in the admin now uses `bg-brand-700 hover:bg-brand-900` instead of `bg-brand-600`, so the "primary action" rule of the artboard holds on all thirteen screens and no small white label sits on a 3.13:1 surface. No other file changed for it.
- L12 (verification, C.T5): `npm run build` (tsc + vite) exit 0; `npx biome check apps/admin/src apps/admin/tailwind.config.js` reports no error in the touched files (the pre-existing `apps/admin/vite.config.ts` trailing-newline complaint is untouched); `npx astryx doctor --built .` reports 20 pass / 3 warn / 0 fail, the three warns being `theme-fonts` (external font import cannot be proven from source) and the `built-astryx-purity` summary of the legacy `<div>` markup that this direction deliberately keeps in Tailwind; every `text-white` in the admin now sits on `bg-brand-700`, `bg-brand-900` or `bg-white/10`; the inherited color resolves to `#000000` because the shell pins `mode="light"`, and both app roots set `text-slate-900` explicitly.
- L13 (bug found by the human after the handoff): "el recuadro de usuario y cerrar sesion solo se muestra en alguna de las vistas, por ejemplo cuando el usario esta en catalago el recuadro esta ausente". Cause: the shell root was `min-h-screen flex`, so on long pages (Catálogo) the `aside` stretched to the full height of the content and its flex column pushed the footer (user + sign-out) below the fold, while `main`'s `overflow-y-auto` was inert because nothing constrained the root height. Fix in `apps/admin/src/components/Layout.tsx`: the root is now `h-screen flex overflow-hidden`, the `aside` is `overflow-hidden`, the `nav` is `flex-1 min-h-0 overflow-y-auto` (it scrolls on its own) and `main` is `flex-1 min-w-0 overflow-y-auto` (it scrolls on its own). The sidebar footer is now pinned to the viewport on every route, and the content scrolls inside `main` instead of the whole page. Verified with `npm run build` and `npx biome check apps/admin/src`; no browser rendering check was possible in this environment, so the visual confirmation is the human's.
- L14 (delivery strategy, slice boundary): the branch `feature/admin-color-system` is cut from `dev`. The authored work is delivered as reviewable work units, each on its own commit: (1) `chore(repo)` allow install scripts; (2) `feat(admin)` Astryx design system + neutral theme wiring; (3) `feat(design)` color directions and design-system sync; (4) `feat(admin)` Mercado fresco direction implementation; (5) `fix(admin)` sidebar footer visible on every route. The last slice closes the feature. The slice counter reported by the harness measures the branch against `master` and therefore also counts the `dev` commits that were already there; the feature's own slices stay under ~400 authored lines each.
